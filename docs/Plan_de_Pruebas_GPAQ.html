Descripcion breve del sistema

GPAQ es una aplicacion web que permite a un administrador gestionar preguntas frecuentes (FAQs) y la configuracion de un asistente virtual. Los usuarios finales interactuan con un widget de chat publico que responde usando la tecnica RAG (Retrieval-Augmented Generation) sobre las FAQs registradas, con integracion opcional a DeepSeek (modo simulado si no hay clave). La autenticacion del panel usa JWT y contrasenas cifradas con bcrypt.

2. Reconocimiento de los Tipos de Prueba

A continuacion se describen los tipos de prueba solicitados y como se aplican concretamente al proyecto GPAQ.

Tipo Definicion Aplicacion en GPAQ
Caja blanca Se prueba conociendo la estructura interna del codigo (logica, ramas, condiciones). El evaluador ve el codigo fuente. Pruebas unitarias con pytest sobre la logica de AuthService (verificacion de contrasena, generacion/validacion de JWT) y validaciones de los modelos Pydantic.
Caja negra Se prueba el sistema por sus entradas y salidas sin conocer la implementacion interna. Peticiones HTTP a los endpoints REST verificando codigos de estado y respuestas (login, CRUD de FAQs, validaciones 422, errores 401/404/405).
Unitarias Verifican una unidad minima de codigo (funcion/metodo) de forma aislada. Suite tests/test_auth.py: login exitoso, login fallido, acceso protegido con/sin token.
Integracion Verifican que varios modulos funcionen correctamente en conjunto. Flujo de chat completo (handler → servicio de chat → repositorios → servicio de IA → MySQL) y flujo Frontend → NGINX (proxy) → API → BD.
Regresion Reejecutar pruebas ya existentes tras un cambio para asegurar que no se rompio nada. Reejecucion de la suite pytest y del conjunto de pruebas de humo (smoke) despues de cada ajuste durante la contenerizacion.
Rendimiento Miden tiempos de respuesta y comportamiento bajo carga normal. Medicion de latencia de GET /health y POST /auth/login (promedio, minimo, maximo, p95).
Esfuerzo (Stress) Someten al sistema a una carga alta o concurrente para observar su estabilidad. Rafaga de 100 peticiones concurrentes (20 en paralelo) a la API para verificar que no haya errores ni caidas.
Usabilidad Evaluan la facilidad de uso y la experiencia del usuario en la interfaz. Evaluacion heuristica de las pantallas: Login, Panel de administracion, Gestor de FAQs, Configuracion del bot y Widget de chat.

3. Planificacion de las Pruebas

3.1 Objetivos y alcance

Objetivo general: validar que el sistema GPAQ cumple con los requisitos funcionales, de seguridad y de calidad esperados antes de su paso a produccion.

Alcance (incluido):

  • API REST: autenticacion, gestion de FAQs, configuracion del bot y chat publico.
  • Frontend servido por NGINX y su comunicacion (proxy) con la API.
  • Persistencia en MySQL e inicializacion automatica de la base de datos.
  • Despliegue con Docker Compose y verificacion de salud (healthchecks) de los contenedores.

Fuera de alcance: pruebas de penetracion avanzadas, integracion real con la IA de pago de DeepSeek (se usa modo simulado) y pruebas en dispositivos moviles fisicos.

4. Objetivos de la Actividad

  • Garantizar accesibilidad para todos los usuarios: verificar que la interfaz sea navegable, con contraste y textos claros, y que el widget de chat sea publico (sin requerir inicio de sesion).
  • Asegurar la calidad previa a produccion: validar despliegue, salud de contenedores y variables de entorno obligatorias antes de liberar.
  • Identificar problemas tempranos y mejorar la calidad del codigo e interfaces: detectar fallos de configuracion, validacion y experiencia de usuario en fase de pruebas.
  • Validar que el sistema cumple con los requisitos del negocio: gestion de FAQs, respuestas automaticas basadas en conocimiento y control de acceso administrativo.

Observaciones generalesEl sistema es estable, seguro y rapido. La validacion de datos (Pydantic), el control de acceso (JWT) y el manejo de errores (401/404/405/422) funcionan correctamente. El despliegue en contenedores es reproducible y exige todas las variables de entorno, evitando arranques mal configurados.
Recomendaciones
  1. En produccion, establecer DOCS_ENABLED=false y usar un JWT_SECRET fuerte y unico.
  2. Para el contenedor MySQL, considerar un usuario de aplicacion con privilegios limitados (en lugar de root) una vez creada la base de datos.
  3. Realizar una auditoria de accesibilidad (Lighthouse/axe) para el criterio US-06.
  4. Anadir pruebas de rate limiting (429) y de expiracion de token para ampliar la cobertura de seguridad.
  5. Integrar la suite pytest en un pipeline de CI para automatizar las pruebas de regresion.
Conclusion: El sistema GPAQ cumple los criterios de aceptacion definidos y se considera apto para pasar a la siguiente fase, atendiendo las recomendaciones indicadas.
